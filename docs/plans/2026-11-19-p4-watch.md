## Goal

The Watch stage works on real data: the connector hub's core, Shopify read through it, routines with the morning
check, and Today, Activity, Library and the bell on the server.

**Success measure (the real slice):** the morning check reads the development store and fills Today.

## Scope

In, in two tracks on one branch:
- **Hub track, wave 2** (one worker at a time, beside P2). It lives only in `app/hub/` and has no server dependency,
  so it starts early, as the runner track does, and reaches `main` only through this phase's ship gate.
  - **Hub core** (also the base for P5): the gateway Worker (`app/hub/`); a `SignIn` Durable Object per connector
    account holding the token in its storage, never in isolate memory; AES-GCM encryption under a versioned key held
    as a Worker secret, with rotation; the read-only scope check; a route registry that each connector directory adds
    to; no public route.
  - **Shopify read:** a Dev Dashboard app per brand with the client credentials grant (24 h tokens the hub refreshes);
    level 1 protected customer data (no names, emails, phones or addresses); `read_returns` in the read scopes; tools
    named `resource_action`; bounded results (a limit, paging and field selection on every read); `sku` as the only
    key on the inventory tool (S5); the recorded Shopify upstream the test build uses.
- **Watch track, wave 4** (after P3 merges):
  - **Hub wiring:** the service binding from the product Worker, the egress route from the runner to the hub, the
    runner's MCP server entry for it (tools loaded on demand through tool search).
  - **Routines:** schedules in D1; a scheduler handler on the BrandAgent object (P3) that starts one run per due slot,
    keyed by the slot; a missed-run rule per routine; single-shot `query()` runs; the `inhouse` routine tools built
    (P3 registered them); the Routines page real (run now, delete, restore, on and off).
  - **The morning check:** a routine that reads the store and returns Today's "needs you" items with their sources as
    structured output, which the server validates and saves.
  - **Today, Activity, Library and the bell** on the server: Today's items and setting one aside, the activity log,
    files in R2 with rows in D1 (by place and type, uploads by the team, the agent's files from P3, safe
    permission-checked downloads, delete and restore), notifications and read state.
  - Nightly connector tests against the read fixture store, never reseeded per run.

Out: OAuth connectors, code mode and Slack (P5); any Shopify write (P6); approvals (P6).

## Inputs and gates

- Hub track: P1 merged into `main` (the shared folder). Watch track: P3 merged into `main`.
- **Prepared from wave 0 (orchestrator, with Wasim):** the read fixture store, seeded once (5 orders a minute, so
  hours; refunds can't be backdated, so dated refunds are made on their day, which is why seeding starts as early as
  it can), using a seed app Wasim installs and removes afterwards; the brand-style Dev Dashboard app with read scopes.
  Credentials reach Workers only through secret cards. No test writes to this store.
- **The recording.** Once the fixture is seeded, the orchestrator records its responses for the read tools (through a
  secret card, on the Mac) into `app/test/upstreams/shopify/recordings/`, with the store's name and host replaced. The
  recording is invented data and fixed, so no test depends on "today".
- Stage gating follows the server's stage (C2): the morning check runs at every stage; routines the team creates need
  Act, as the demo shows.
- **Test model (Wasim, 2026-11-19):** every test, eval, smoke or check in this phase that calls a real model runs on
  Sonnet 5.5 (`claude-sonnet-5-5`) at medium effort; everything else uses the scripted model.

## Design notes

- **Hub layout.** `app/hub/` with its own `package.json` and its own config template `app/wrangler.hub.jsonc` (no
  account ids), so the early track never touches `app/package.json`. Connectors live in
  `app/hub/connectors/<tool>/`, each with its own route file that the hub entry's registry loads, so later connectors
  never edit the entry. The product Worker never holds a tool token. A hub job in this branch's `ci.yml` runs its
  types and tests from wave 2.
- **The hub in tests.** CI and the test build run the product Worker and the hub together under multi-config
  `wrangler dev`, each run with its own local `SignIn` storage, against the recorded Shopify upstream. No store
  credential is in CI, a preview or the sandbox account. The real store is read in three places only (schedule,
  "Where backend phases are proven"): the orchestrator's live check before the ship packet, the nightly on the house
  deployment, and the release smoke.
- **Releasing the hub.** The hub deploys before the product Worker and rolls back with it, as a pair, to the previous
  tag. It has no public route: the config check fails a hub config with one, and an API spec shows it answers only
  the service binding. Its encryption key is set through a secret card.
- **Morning check output** is a typed list (the shared schema's Today item: severity, area, title, sources, the numbers
  as `{ minor, currency }` and instants as `{ iso, ms }`). The routine run returns it as the run's structured result;
  the server validates it against the schema and saves it. There's no Today tool: the `inhouse` server keeps its 20.
  An invalid result fails the run, shown in Activity; Today never parses prose. The orchestrator confirms the SDK's
  structured output option in its docs at the Plan step.
- **Who a routine runs as.** A routine belongs to the brand (BD11: what a chat makes is visible to the team). Its runs
  act as the routine's own system principal, with the creator recorded on each run. They read brand memory, never a
  person's, since the team can open the trace. Removing the creator doesn't stop the routine; an admin can pause or
  delete it. From P6, a question it asks goes to its creator, or to the admins once the creator is gone.
- **Slots.** A slot is keyed by routine, local date and scheduled local time in the brand's time zone. A local time
  the clock skips (spring forward) runs at the next valid minute. A local time that happens twice (fall back) runs
  once, the first time. The slot row is written before the run is created, and run creation is idempotent on the slot
  key, so a crash between the two is picked up by the handler's sweep and can't run the slot twice.
- **What the Library shows.** Files the agent made and files the team uploaded are visible to the team. A chat's
  transcript and the files a person attached to their own messages stay private to that person (BD11 protects the
  conversation, not what it makes).
- **Serving files.** Every download is an attachment with `nosniff` and `Content-Security-Policy: sandbox`. HTML and
  SVG never render in the app's origin: a file the agent was tricked into making could otherwise act with the
  member's session.
- **Prompts** live in `app/server/prompt/` (orchestrator only). A prompt change runs the eval suite and the
  morning-check set before it merges.
- **Wave ownership.** In wave 4, W4 owns `src/agent/mock.ts` and the settings pages; P5's edits to them wait for W4's to
  reach P5's branch (see the schedule).
- Every migration PR adds its table registry entry (`app/ops/tables/<resource>.ts`).

## Acceptance

1. A routine runs once per slot under repeated alarms (tested against the real scheduler by firing the alarm twice);
   a missed slot follows its rule; a skipped local time runs at the next valid minute and a repeated one runs once (a
   property test across daylight-saving changes in the brand's time zone); a crash between the slot row and the run
   ends with exactly one run.
2. The morning-check set passes its threshold on the recorded upstream (at least 90% of graded cases, and no item
   raised on the clean cases); Today reads only validated typed items; an invalid result fails the run and saves
   nothing; the `inhouse` server still has exactly 20 tools.
3. Every Shopify read returns at most its bound, pages beyond it, and never a level 2 field (a test asserts the field
   list).
4. The hub refreshes the 24 h token before expiry; a token never appears in the product Worker, the container or a log
   (a canary token test); key rotation re-encrypts, and old tokens decrypt until rotated.
5. The runner has no write path: a write operation sent through the runner's scope is refused at the hub. The hub has
   no public route.
6. A routine run acts as the routine principal, reads no person's memory, and keeps running after its creator is
   removed.
7. Files the agent made are visible to the team; a Member can't fetch another person's chat attachment or
   transcript; every download is an attachment with `nosniff` and a sandboxing CSP, and an HTML or SVG file never
   renders in the app's origin.
8. A routine the team creates is refused at Watch and allowed at Act.
9. The nightly connector tests pass against the read fixture without reseeding it; the live check passed on the final
   PR's head.
10. API specs and the contract suite pass for the P4 methods; the exfiltration cases added here have zero bypasses.
11. QA PASS and the ship recording on S1 to S8; after the release (hub first, then the product Worker), the real-model
    smoke passes on the house deployment.

## Must not

No tool token outside the hub's `SignIn` storage; no store credential in CI, a preview or the sandbox account; no
Shopify write; no write of any kind to the read fixture; no level 2 customer field; no unbounded read reaching the
model; no 21st `inhouse` tool; no real brand store in tests or previews; no public route on the hub; no agent-made file
rendered in the app's origin; no edit to the BrandAgent object (register a handler instead); no retries in tests.

## Risks

- Seeding at 5 orders a minute and refunds on their day: start in wave 0, record the fixture's shape, never depend on
  "today" in assertions.
- Shopify API version changes: pin the version and test it nightly. A recording can go stale against a new version,
  so a version bump re-records.
- Morning check quality depends on prompts: the graded set gates prompt changes.
- The hub is new infrastructure that P5 builds on; H0 lands early and is reviewed at high.
- `fleet/watch` lives from wave 2 to wave 4. `main` merges in after P2 and P3; the hub's own package keeps that quiet.

## How it lands

- Branch `fleet/watch` from `main` after P1 merges (the hub track); the Watch track starts after P3 merges.
- Review rows: H0, H1, W2 and every migration at Sonnet plus Opus high (tokens, concurrency, schema); W1, W3 to W6
  Sonnet plus Opus medium; prompt changes go with their eval results.
- Final PR with the full ship gate; the house release (hub, then product) and real-model smoke follow, with Wasim's
  OK.
