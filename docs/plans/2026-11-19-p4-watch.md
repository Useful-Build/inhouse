# P4: Watch (`fleet/watch`)

Status: draft, 2026-11-19, revised after the Sonnet and Opus review. Phase plan under the backend plan
(`docs/plans/2026-11-19-backend.md`). Common rules are in its "Phase schedule (waves)" section. P0 records:
[S4](../decisions/p0-s4-connector-hub.md), [S5](../decisions/p0-s5-memory-tool-choice.md).

## Goal

The Watch stage works on real data: the connector hub's core, Shopify read through it, routines with the morning
check, and Today, Activity, Library and the bell on the server.

**Success measure (the real slice):** the morning check reads the development store and fills Today.

## Scope

In:
- **Hub core** (first piece, also the base for P5): the gateway Worker (`app/hub/`), reached from the product Worker
  by a service binding; a `SignIn` Durable Object per connector account holding the token in its storage, never in
  isolate memory; AES-GCM encryption under a versioned key held as a Worker secret, with rotation; the runner's scope
  read only; the egress route from the runner to the hub and the runner's MCP server entry for it; a route registry
  that each connector directory adds to.
- **Shopify read:** a Dev Dashboard app per brand with the client credentials grant (24 h tokens the hub refreshes);
  level 1 protected customer data (no names, emails, phones or addresses); `read_returns` in the read scopes; tools
  named `resource_action`, loaded on demand through tool search; bounded results (a limit, paging and field selection
  on every read); `sku` as the only key on the inventory tool (S5).
- **Routines:** schedules in D1; a scheduler handler on the BrandAgent object (P3) that starts one run per due slot,
  keyed by the slot; a missed-run rule per routine; single-shot `query()` runs; the `inhouse` routine tools built
  (P3 registered them); the Routines page real.
- **The morning check:** a routine that reads the store and writes Today's "needs you" items with their sources.
- **Today, Activity, Library and the bell** on the server: Today's items, the activity log, files in R2 with rows in D1
  (by place and type, uploads by the team, the agent's files through P3's file-save route, permission-checked
  downloads, delete and restore), notifications and read state.
- Nightly connector tests against the read fixture store, never reseeded per run.

Out: OAuth connectors, code mode and Slack (P5); any Shopify write (P6); approvals (P6).

## Inputs and gates

- P3 merged into `main`.
- **Prepared during wave 3 (orchestrator, with Wasim):** the read fixture store, seeded once (5 orders a minute, so
  hours; refunds can't be backdated, so dated refunds are made on their day), using a seed app Wasim installs and
  removes afterwards; the brand-style Dev Dashboard app with read scopes. Credentials reach Workers only through secret
  cards. No P4 test writes to this store.
- Stage gating follows the server's stage (C2): the morning check runs at every stage; routines the team creates need
  Act, as the demo shows.
- **Test model (Wasim, 2026-11-19):** every test, eval, smoke or check in this phase that calls a real model runs on
  Sonnet 5.5 (`claude-sonnet-5-5`) at medium effort; everything else uses the scripted model.

## Design notes

- **Hub layout.** `app/hub/` with its own config template `app/wrangler.hub.jsonc` (no account ids). Connectors live in
  `app/hub/connectors/<tool>/`, each with its own route file that the hub entry's registry loads, so later connectors
  never edit the entry. The product Worker never holds a tool token.
- **The hub in tests.** CI and the test build run the product Worker and the hub together under multi-config
  `wrangler dev`, each run with its own local `SignIn` storage. The sandbox account has one shared hub deployment that
  holds only the read fixture store's read-only credentials; previews bind to it. That's acceptable because it's
  invented data and read only; anything that writes or connects a new account is tested under `wrangler dev`, never on
  the shared hub.
- **Morning check output** is a typed list (the shared schema's Today item: severity, area, title, sources, the numbers
  as `{ minor, currency }` and instants as `{ iso, ms }`). The routine writes through an `inhouse` tool, never free
  text, so Today never parses prose.
- **Prompts** live in `app/server/prompt/` (orchestrator only). A prompt change runs the eval suite and the
  morning-check set before it merges.
- **Wave ownership.** In wave 4, W4 owns `src/agent/mock.ts` and the settings pages; P5's edits to them wait for W4's to
  reach P5's branch (see the schedule).

## Browser scenarios (`e2e/ship/watch.spec.ts`, desktop and phone, test build with the hub, read fixture, scripted model where the answer must be fixed)

- S1: Run the morning check from Routines; Today fills with the store's items and the right count.
- S2: Open an item; the problem panel shows the orders behind it from the store.
- S3: Ask which orders are late; the answer streams with a bounded table and its sources.
- S4: Activity shows the morning check's run with its time.
- S5: The bell shows the new notice; marking it read clears the dot after a reload.
- S6: Library shows a file the agent made; it downloads; deleting and restoring it works.
- S7: Routines shows the morning check's next run on the brand's time zone.

## Acceptance

1. A routine runs once per slot under repeated alarms (tested by firing the alarm twice); a missed slot follows its
   rule; a property test shows slots stay right across daylight-saving changes in the brand's time zone.
2. The morning-check set passes its threshold on the read fixture (at least 90% of graded cases, and no item raised on
   the clean cases); Today reads only typed items.
3. Every Shopify read returns at most its bound, pages beyond it, and never a level 2 field (a test asserts the field
   list).
4. The hub refreshes the 24 h token before expiry; a token never appears in the product Worker, the container or a log
   (a canary token test); key rotation re-encrypts, and old tokens decrypt until rotated.
5. The runner has no write path: a write operation sent through the runner's scope is refused at the hub.
6. Library downloads are permission-checked; a Member can't fetch another person's chat file.
7. A routine the team creates is refused at Watch and allowed at Act.
8. The nightly connector tests pass against the read fixture without reseeding it.
9. API specs and the contract suite pass for the P4 methods.
10. QA PASS and the ship recording on S1 to S7; the real-model smoke passes on the house deployment.

## Must not

No tool token outside the hub's `SignIn` storage; no Shopify write; no write of any kind to the read fixture; no level
2 customer field; no unbounded read reaching the model; no real brand store in tests or previews; no edit to the
BrandAgent object (register a handler instead); no retries in tests.

## Risks

- Seeding at 5 orders a minute and refunds on their day: start in wave 3, record the fixture's shape, never depend on
  "today" in assertions.
- Shopify API version changes: pin the version and test it nightly.
- Morning check quality depends on prompts: the graded set gates prompt changes.
- The hub is new infrastructure that P5 builds on; H0 lands first and is reviewed at high.

## How it lands

- Branch `fleet/watch` from `main` after P3 merges.
- Review rows: H0, W2 and every migration at Sonnet plus Opus high (tokens, concurrency, schema); W1, W3 to W6 Sonnet
  plus Opus medium; prompt changes go with their eval results.
- Final PR with the full ship gate; the house release and real-model smoke follow, with Wasim's OK.
