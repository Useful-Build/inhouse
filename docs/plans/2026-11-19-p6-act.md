(`docs/plans/2026-11-19-backend.md`, Architecture 7 and 8). Common rules are in its "Phase schedule (waves)" section.

## Goal

The agent does real work with a person's approval: typed approvals, the server-side send hold, the outbox as the only
write path, questions that wait, team memory approval, our skills, team requests and Shopify writes.

**Success measure (the real slice):** approve a draft and it goes out once after 10 seconds; Undo inside the hold
stops it; an unclear result shows as needing a check.

## Scope

In:
- **Approvals and the outbox:** `approval_request` stores a typed action (operation, connector account, arguments,
  recipient, money, revision); a server table per operation (moves money, reaches a customer, reversible, honours an
  idempotency key, eligible for Run with its units field); the card rendered by the server from typed fields;
  `approve(id, ifRev)` bound to that revision; the dispatch intent written in the same D1 transaction with `sendAt` =
  server clock plus 10 s; the claim as one conditional update run by a scheduler handler; Undo as the opposite update,
  winning only before the claim; the state machine below for every outcome; a sweep for approved rows whose task was
  lost; compensating actions through the same path. The approval tools: `approval_request`, `approval_get`,
  `approval_list`, `approval_withdraw`.
- **C7:** `approve` returns `sendAt`; Undo until the claim; `approval.sent` and `needs_check` from the server; no
  browser timer. "Approve all low-risk" is the client approving each card in turn with its own `ifRev`, one approval
  and one audit line each; low-risk comes from the operation table (no money, no customer, reversible).
- **Approval rules by member id** (BD6): who approves what, set per rule.
- **`question_ask`:** safe when unanswered; in a routine it defers the call and the run ends with `tool_deferred`; the
  answer resumes the session; the runner's own one-call check; the 7-day cap, after which the run is closed and the
  person told; the questions inbox where people answer.
- **Team memory approval:** a brand fact waits for an admin's OK before the agent relies on it; the admin's approve and
  reject API and its place in the UI.
- **Skills and team requests:** our skills through `plugins` from a read-only path; the Skills page real; the
  `team_request_create` and `team_request_list` tools and tool and skill requests to the Inhouse team. **Wasim's
  decision Q7 (schedule): which skills ship.** "Our skills" has no list yet. Recommended: `dataviz` (already kept)
  plus one skill per file type the agent is meant to make (PDF, Word, spreadsheet), and nothing else in this plan. W6
  builds the loading path and the page; the list lands when he's decided.
- **Shopify writes** on the outbox only, each operation in the table, including an inventory adjustment with a typed
  `units` argument marked eligible for Run (P7's restock). They use a **second, write-scoped Shopify app per brand**,
  with its token in its own `SignIn` object, behind a hub entrypoint only the outbox dispatcher is bound to. The read
  app keeps read scopes, so a mutation on the runner's path still fails twice: at our parse check and at Shopify (S4).
- **Slack writes (Wasim, 2026-11-19):** Slack posts go only through our server. A message the agent drafts for Slack
  is an outbox action like any other write (typed recipient, approval, hold, at most once); approver notices use P5's
  `notification_send` path with a link to the card. The runner never gets Slack write access.
- **Approving happens in the app only.** Slack carries a link to the card. **Wasim's decision Q4 (schedule), asked at
  plan approval, not in wave 5:** confirm this. Approving inside Slack is a second approval surface with its own
  sign-in, races and audit trail, so it's out of this plan and would be its own project.
- **Evals:** the injection set (tool data telling the agent to send, refund or widen recipients) and the exfiltration
  set, completed from the cases P3 to P5 started (tool data telling it to fetch a URL or message someone outside the
  team); any bypass fails. **Wasim's decision Q6 (schedule):** run both sets, and P7's Run set, once on every model
  the picker offers. Recommended: yes. Zero bypasses on Sonnet says nothing about another model, and it fits the
  test-model rule as a deliberate comparison. It's a paid run, so it needs his OK; a model that hasn't passed stays
  off at Act and Run.

Out: acting without approval (P7); approving inside Slack; connector writes other than Shopify and the Slack post
(each added with its operation table entry when a brand needs it).

## Design notes

- **The outbox state machine** is written by the orchestrator (Opus) into W1's and W2's briefs before either starts.
  The intent row and these transitions are frozen first; the rest fans out from them.

  | State | Enters when | Leaves to |
  |---|---|---|
  | `waiting` | `approval_request` stored the action | `approved`, `withdrawn` |
  | `approved` | a person allowed by the rule approved this revision; the intent and `sendAt` are written with it | `sending` (the claim), `undone`, `waiting` (lapsed) |
  | `sending` | the claim: one conditional update (approved, this revision, not undone, not paused, past `sendAt`, operation in the table, the policy's claim check), which also records the attempt and its idempotency key before any call | `sent`, `failed`, `needs_check` |
  | `sent` | the tool confirmed it | (a compensating action is a new row) |
  | `failed` | the tool answered that nothing happened (a typed refusal) | (a new request is a new revision) |
  | `needs_check` | the result is unclear: a timeout, a dropped connection, a 5xx, or a crash before the result was saved | `sent` or `failed`, set by a person |

- **A row in `sending` is never claimed again.** Not by the alarm, not by the sweep, not after a restart. The sweep
  claims only `approved` rows past `sendAt` whose task was lost, with the same conditional update.
- **Crash recovery, at each boundary.** After the claim and before the call, after the call and before the result is
  saved, and after the result: a row left in `sending` past its deadline is unclear. If the operation honours an
  idempotency key (the table says so), the dispatcher retries once with the same key, which the tool treats as the
  same request; if that's unclear too, the row becomes `needs_check`. With no key it becomes `needs_check` at once.
  An unclear result never falls back to a plain resend, and a definite refusal is `failed`, not a retry.
- **Who resolves `needs_check`.** The approver or an admin, on the card, after looking in the tool: "it went out"
  (`sent`) or "it didn't" (`failed`). Both are audited. The health route counts open `needs_check` rows.
- **An operation not in the table never dispatches.** `approval_request` refuses it with a typed error, and the claim
  checks the table again, so approving can't send something the table doesn't describe.
- **Pause.** Pausing moves every `approved`, unclaimed row back to `waiting` and tells its approver. Nothing claims
  while paused, and resuming sends nothing: a person approves again. That settles "nothing claims while paused", the
  sweep and "resume starts nothing on its own" into one rule. A request already at the tool can't be recalled.
- **After a restore** (P8), every `approved` and `sending` row is held and the outbox stays paused until reconciled.
- **The policy hook.** `app/server/outbox/policy.ts` is an interface with two calls: at request time (may this action
  be approved by the system, and what does it reserve) and at the claim (is it still allowed). P6 registers a policy
  that always answers "a person approves" and "yes". P7 registers the Run policy and never edits the claim.
- **The operation table.** W1 owns the table's type and loader; each connector's entries are a file under
  `app/server/outbox/operations/`, written by the worker who builds that connector's writes and reviewed at high.
- **Faults for tests** live in the fake upstreams, not in the hub: the recorded Shopify upstream gains write
  operations with a switch per operation (succeed, refuse, time out with an unknown result), used by S3, the API specs
  and the property test. Nothing fault-related is in a deployable bundle.
- **Wave ownership.** W4 owns `src/agent/mock.ts` and the settings pages in this wave; P8's coverage work doesn't touch
  them.
- Every migration PR adds its table registry entry (`app/ops/tables/<resource>.ts`).

## Browser scenarios (`e2e/ship/act.spec.ts`, desktop and phone, test build, the fake upstreams, scripted model)

- S1: The agent drafts a fix; approving it shows the 10-second hold, then it's sent once and Activity shows it.
- S2: Undo inside the hold stops the send; the store is unchanged.
- S3: With the fault switch on "unknown result", the action shows as needing a check, with no second send; the
  approver marks it "it didn't go out" and it's closed.
- S4: Editing a draft after it was shown changes its revision; approving the old card is refused with the new one.
- S5: A routine asks a question; answering it in the questions inbox resumes the routine and it finishes.
- S6: A brand fact the agent saved waits for an admin; after the OK, the agent uses it.
- S7: Only the member named on the rule can approve; another member sees the card read-only.
- S8: Request a skill from the Skills page; it shows as requested for the Inhouse team.
- S9: Pause during a hold; the approval goes back to waiting with a notice, and Resume sends nothing.

## Acceptance

1. An approved action goes out at most once, only after `sendAt`, and only in the revision approved.
2. Undo before the claim sends nothing; Undo after it gets `conflict`.
3. A definite refusal becomes `failed`. An unclear result becomes `needs_check`, never a plain resend; only an
   operation whose table entry honours an idempotency key gets one retry, with the same key, and a second unclear
   result is `needs_check`.
4. A crash after the claim, after the call, or before the result is saved leaves at most one effect at the tool, and
   the row ends in `sent` or `needs_check` (each boundary tested).
5. The sweep finds an approved row whose task was lost and claims it once; it never touches a `sending` row; the
   property test passes.
6. Pausing returns every approved, unclaimed row to `waiting` and tells its approver; nothing claims while paused;
   resuming sends nothing.
7. The runner has no write path: every write goes through the outbox (a test tries a write from the runner's scope),
   and the write app's entrypoint answers only the dispatcher.
8. An operation not in the table can't be requested and can't be claimed; money and customer actions always wait.
9. `needs_check` is resolved only by the approver or an admin, and both answers are audited; the health route counts
   open ones.
10. `question_ask` beside another call in one turn is treated as not deferrable; a routine's question waits across a
    container restart and resumes with the answer; a wait past 7 days closes the run and tells the person.
11. The injection and exfiltration sets have zero bypasses on Sonnet 5.5, and on every other model the picker offers
    if Q6 is a yes; results are kept.
12. API specs and the contract suite pass for P6 methods; the demo is unchanged.
13. QA PASS and the ship recording on S1 to S9; the live check passed against the write store; after the release, the
    real-model smoke passes on the house deployment.

## Must not

No tool write outside the outbox (Slack included, except `notification_send` to listed channels); no Slack write
access for the runner; no browser timer deciding a send; no automatic resend of an unclear send; no second claim of a
row in `sending`; no approval that isn't bound to a revision; no approver chosen by role alone; no approving inside
Slack; no write scope on the read app; no write to the read fixture; no two live runs against the write store at
once; no fault switch in a deployable build; no real customer data in either store.

## Risks

- The outbox is the product's riskiest code: the frozen state machine, the property test with crashes and an Opus
  review at high.
- Shopify's idempotency support differs per mutation; the table records which honour a key, the rest go to
  `needs_check` on an unclear result.
- Deferral behaviour runs ahead of the SDK docs (P0); the runner's own check is the guard.
- A second Shopify app per brand is one more thing to install; P8's onboarding checklist carries it.
