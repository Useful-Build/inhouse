# P6: Act (`fleet/act`)

Status: draft, 2026-11-19. Phase plan under the backend plan (`docs/plans/2026-11-19-backend.md`, Architecture 7 and
8). Common rules are in its "Phase schedule (waves)" section.

## Goal

The agent does real work with a person's approval: typed approvals, the server-side send hold, the outbox as the only
write path, questions that wait, team memory approval, our skills and Shopify writes.

**Success measure (the real slice):** approve a draft and it goes out once after 10 seconds; Undo inside the hold
stops it; an unclear result shows as needing a check.

## Scope

In:
- **Approvals and the outbox:** `approval_request` stores a typed action (operation, connector account, arguments,
  recipient, money, revision); a server table per operation (moves money, reaches a customer, reversible, honours an
  idempotency key), where an unknown operation always waits; the card rendered by the server from typed fields;
  `approve(id, ifRev)` bound to that revision; the dispatch intent written in the same D1 transaction with `sendAt` =
  server clock plus 10 s; the alarm's claim as one conditional update; Undo as the opposite update, winning only before
  the claim; retry with the same key where the tool honours one, else `needs_check`; a sweep for approved rows whose
  alarm was lost; compensating actions through the same path.
- **C7:** `approve` returns `sendAt`; Undo until the claim; `approval.sent` and `needs_check` from the server; no
  browser timer.
- **Approval rules by member id** (BD6): who approves what, set per rule.
- **`question_ask`:** safe when unanswered; in a routine it defers the call and the run ends with `tool_deferred`; the
  answer resumes the session; the runner's own one-call check; the 7-day cap.
- **Team memory approval:** a brand fact waits for an admin's OK before the agent relies on it.
- **Skills:** our skills loaded through `plugins` from a read-only path; the Skills page real (requests go to the
  Inhouse team).
- **Shopify writes** on the outbox only, each operation in the table.
- **Evals:** the injection set (tool data telling the agent to send, refund or widen recipients) and the exfiltration
  set (tool data telling it to fetch a URL or message someone outside the team); any bypass fails.
- Slack notifies approvers with a link to the card; approving happens in the app (see the decision below).

Out: acting without approval (P7); connector writes other than Shopify (each added with its operation table entry
when a brand needs it).

## Inputs and gates

- **Wasim's decision:** approving only in the app, with Slack carrying a link (recommended: one approval path, one
  audit trail), or approving from Slack too.
- The fixture store gets a write-scoped app for P6's tests, on the same invented data; writes there are tested as

## Browser scenarios (`e2e/ship/act.spec.ts`, desktop and phone, fixture store, scripted model)

- S1: The agent drafts a fix; approving it shows the 10-second hold, then it's sent once and Activity shows it.
- S2: Undo inside the hold stops the send; the store is unchanged.
- S3: An unclear result from the tool shows the action as needing a check, with no second send.
- S4: Editing a draft after it was shown changes its revision; approving the old card is refused with the new one.
- S5: A routine asks a question; answering it resumes the routine and it finishes.
- S6: A brand fact the agent saved waits for an admin; after the OK, the agent uses it.
- S7: Only the member named on the rule can approve; another member sees the card read-only.

## Acceptance

1. An approved action goes out at most once, only after `sendAt`, and only in the revision approved.
2. Undo before the claim sends nothing; Undo after it gets `conflict`.
3. An unclear result becomes `needs_check`, never a resend; a tool with an idempotency key is retried with the same key.
4. The sweep finds an approved row whose alarm was lost and claims it once.
5. The runner has no write path: every write goes through the outbox (a test tries a write from the runner's scope).
6. An operation not in the table always waits; money and customer actions always wait.
7. `question_ask` beside another call in one turn is treated as not deferrable; a wait past 7 days closes the run.
8. The injection and exfiltration sets have zero bypasses; results are kept.
9. API specs and the contract suite pass for P6 methods; the demo is unchanged.
10. QA PASS and the ship recording on S1 to S7.

## Must not

No tool write outside the outbox; no browser timer deciding a send; no automatic resend of an unclear send; no approval
that isn't bound to a revision; no approver chosen by role alone; no real customer data in the fixture store.

## Risks

- The outbox is the product's riskiest code. A state-machine property test (fast-check over approve, Undo, alarm,
  retry and sweep orders) is part of W1, and Opus reviews at high.
- Shopify's idempotency support differs per mutation; the table records which honour a key, the rest go to
  `needs_check` on an unclear result.
- Deferral behaviour runs ahead of the SDK docs (P0); the runner's own check is the guard.
