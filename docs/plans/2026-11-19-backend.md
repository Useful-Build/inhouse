# Backend plan: the real Inhouse agent

Status: approved by Wasim, 2026-11-19. Revised after simplest-path and second opinions from Claude
Fable 5.2 (xhigh) and GPT 6.2 Sol via Pi (xhigh). Runs after the hardening plan (`docs/plans/2026-11-19-production.md`)
and lands through the setup plan's landing flow (`docs/plans/2026-11-19-setup-gaps.md`): one `fleet/<topic>` branch per
project, worker PRs into it, per-PR previews, the QA gate, a ship recording Wasim watches, his approval of the exact
SHA. Platform claims were checked against current docs on 2026-11-19; the URL is cited where the claim is made.

## Goal

Replace the mock with the real agent, built on the Claude Agent SDK and hosted on Cloudflare, behind the screens that
exist today, at all three stages (Watch, Act, Run), and prove with tests that the frontend and backend agree and hold up
on real data. The mock stays as the public demo; the product never ships sample data.

**Success measure:** the house deployment runs Watch, Act and Run on a Shopify development store for two weeks with no
approval bypass and no lost or doubled send; the same contract suite passes on the mock and the real client on every
PR; every phase shipped through the ship gate.

## Deployment model

- **One deployment per brand, in the brand's own Cloudflare account,** on the brand's own Anthropic key. Each brand has
  its own Worker, Durable Objects, container, D1 database, R2 bucket and AI Gateway. Nothing is shared between brands:
  the account boundary is the tenant boundary, so there is no tenant column to forget.
- **The house deployment** in our account, on our key, is where each release runs first (staging and canary).
- **A sandbox account** holds the per-PR previews: invented data, the scripted model, no real keys or tokens.
- **The demo deployment** stays as it is: public, mock only, sample data, no backend.
- **One codebase, one release, many accounts.** Which brands exist and their settings live in a private ops repo.

## Decisions

Wasim's calls (2026-11-19, on top of the product decisions):
- BD1 The engine is the Claude Agent SDK in Cloudflare Containers. The Cloudflare Agents SDK is not the agent loop.
- BD2 One deployment per brand in the brand's own account, on the brand's own Anthropic key; the house deployment on
  ours.
- BD3 All three stages are built: Watch, Act and Run.
- BD4 Tools in this plan: our 20 `inhouse` tools, the engine's built-in tools we keep (under the container guards), and
  connecting tools that publish an official MCP server (commerce tools, Slack). A connector for a tool with no MCP
  server is built when a brand that uses it is onboarded, outside this plan.
- BD5 Staff login is Cloudflare Access in the brand's account.

Wasim's calls on my recommendation (2026-11-19):
- BD6 Roles are Member, Admin and Inhouse team; approving is set per rule, by member id, not a role.
- BD7 The Inhouse team sees health, errors and usage numbers by default, and a brand's chats, memory and audit log only
  while an admin has granted time-boxed support access, which is logged. Amended 2026-11-20 (decision 19): the Inhouse
  team also holds every Admin control (members, brand settings, models, pause, tools) without a grant; only chats,
  memory and the audit log need the grant, and only an Admin grants it. Decision 19b (2026-11-20): the Inhouse team
  can't change roles, invite an Admin or remove an Admin.
- BD8 Shopify is the exception to BD4: there is no hosted MCP server for its Admin API, every brand has it and Watch
  shows nothing without it, so our Shopify connector (read first, then the writes Act and Run need) is in this plan.
- BD9 Bedrock is a manual, per-brand switch in the brand's own AWS account, turned on after the agent evals pass on it.
  No automatic failover, and a half-done run is never replayed on the other provider.
- BD10 Durable Object alarms, not Workflows, run the send hold, routine schedules and long waits. A Workflow binding in
  a preview runs the deployed Workflow's code and shares its instances
  ([Previews](https://developers.cloudflare.com/workers/previews/resources/)), while Durable Objects get their own
  storage per preview. Alarms keep every per-PR preview fully isolated and drop a moving part. This changes the
  product decisions' hosting list (which names Workflows).
- BD11 A chat belongs to the person who started it. Others don't see it; what it makes (an approval, a routine, a file)
  is visible to the team as usual.
- BD12 No UK-only or EU-only processing promise for now. D1 and R2 can pin where data rests
  ([D1](https://developers.cloudflare.com/d1/configuration/data-location/),
  [R2](https://developers.cloudflare.com/r2/reference/data-location/)), but containers, Durable Objects, inference,
  logs and connectors don't follow it. Each brand gets a documented data flow instead.
- BD13 Brand deployment settings, monitor targets and the brand release workflow live in a private ops repo.

## Architecture (one brand)

```
Browser ──Access──> App Worker ──── D1 (records, FTS5)        R2 (files, transcripts, backups)
                      │  /api/*, WebSocket /live
                      ├── BrandAgent Durable Object ── runner DOs (pool) ── ctx.container ── runner (Node + Claude Agent SDK)
                      │     live runs, event log, alarms:                                          │ every outbound call intercepted
                      │     send hold, routines, waits, kill switch                                ▼
                      ├── egress entrypoint <───────────────────────────────────────────── model, inhouse MCP, connector reads,
                      │     allowlist, run scope, log of record                                   session store, file saves
                      ├── outbox dispatcher (the only path that writes to a tool)
                      └── AI Gateway (brand's key, payload logging off) ── Anthropic (Bedrock by switch)
```

1. **App Worker.** Serves the product build and `/api/*`. Verifies the Access JWT on every request and on the WebSocket
   upgrade, against a configured issuer and audience, and fails closed
   ([validating JWTs](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)).
   Maps the identity provider's stable subject (not only the email) to a member and role in D1. Checks every
   permission on the object, not just the route: whose chat, which trace, which approval, an unexpired support grant.
   Removing a member or ending a grant closes their sockets and ends their runs' authority.
2. **BrandAgent Durable Object, one per brand.** Routes runs to a small pool of runner Durable Objects
   (`runner-0..N`), each owning one container through `ctx.container` (this pool replaces one container per brand;
   decided, Wasim 2026-11-19)
   ([container API](https://developers.cloudflare.com/containers/api/); the older `Container` class is
   [deprecated](https://developers.cloudflare.com/containers/guides/migrate-to-durable-object-container-api/)), on the
   `default` scheduling policy. One container can't scale on its own: each instance belongs to one Durable Object
   ([scaling](https://developers.cloudflare.com/containers/platform-details/scaling-and-routing/)). Sizing from P0
   ([S1](../decisions/p0-s1-runner.md)): standard-4 containers; containers = max(2, ceil(peak concurrent runs / 25)),
   routed fill-first so extra containers wake only at peaks; `max_instances` at least 3 times the need. A placement
   refusal ("There is no container instance that can be provided to this Durable Object, try again later") is normal,
   not a failed run: route to a running container, queue briefly when all are full.
   Holds live runs: an event log per run with sequence numbers in its SQLite storage, fan-out to WebSockets with
   [hibernation](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), reattach from a
   sequence number, `send`, `interrupt` and `stop` by turn id, the per-brand concurrent-run limit and the Pause switch.
   It names each chat's session up front (`sessionId` on the first run, `resume` after), so a run stopped mid-way can
   still resume, and keeps the per-run token table the egress checks (see 4).
   Its alarm drives the send hold, routine schedules, retention and backups
   ([alarms](https://developers.cloudflare.com/durable-objects/api/alarms/): at least once, so every handler is
   idempotent). Finished messages go to D1.
3. **The runner.** A small Node server in the container wrapping the Claude Agent SDK, which runs the Claude Code CLI
   as a subprocess and needs a disk, so it can't run in a Worker ([hosting](https://code.claude.com/docs/en/agent-sdk/hosting)).
   Each container runs several sessions (about 25 runs at once on standard-4; CPU binds first, at under 1 CPU-second
   and about 170 MB per run). One `query()` per run, closed when the run ends and resumed from the
   session store for the next one, so idle chats hold no memory or budget. `settingSources: []`, auto memory off, a
   stable working-folder path per chat (the store's key comes from it). **`process.report.excludeNetwork = true` is set
   before the SDK loads:** with internet off, the SDK's libc check otherwise reverse-resolves every open socket and
   stalls each start by 60 s to several minutes (P0 S1 and S2: 1.8 s cold and 0.8 s warm to init with it, 394 s
   without). A deferred call resumes with prompt `""`; an empty prompt stream loses the in-process MCP server.
   Transcripts mirror to our `sessionStore` on R2
   ([session storage](https://code.claude.com/docs/en/agent-sdk/session-storage)); mirroring is best effort, so a
   checkpoint is confirmed in the store before a run is marked waiting, and `mirror_error` is reported. The checkpoint
   is concrete: the runner keeps every batch until the store confirms it, re-sends a dropped batch under its original
   part id, then checks the run's entries with `load()`; only then is the chat marked waiting (P0: without the repair
   the resume fails). With the default batched flush a hard container kill loses that turn's transcript, so the runner
   mirrors during the turn (`sessionStoreFlush: 'eager'`, alpha, tested in P3); until that holds it's an accepted gap:
   the run restarts from its last completed run and the person is told. Skills load
   through `plugins` from a read-only path, never from a folder the agent can write
   ([skills](https://code.claude.com/docs/en/agent-sdk/skills)). On SIGTERM the runner ends live queries with
   `interrupt()`, flushes the store and marks live runs interrupted (abort alone didn't end the turn loop in P0). The
   container's inactivity timeout is set again on every run: a recreated Durable Object that found its container
   running didn't set it, and the platform stopped the container under live runs.
4. **Container guards** (the approved design, tightened). Internet off; every outbound call
   [intercepted](https://developers.cloudflare.com/containers/configuration/outbound-traffic/) to the egress
   entrypoint, which pins upstream hosts, validates requests and redirects, and adds credentials. No model key, tool
   token or secret in the container (the model key is added at the gateway, as in Cloudflare's
   [sandbox example](https://developers.cloudflare.com/sandbox/coding-agents/claude-code/)). The runner holds a run
   token in memory only: scoped to one run and person, expiring with the run, never accepted on `/api/*`, never in a
   tool subprocess's environment. Intercepts are per container, so run tokens are checked against a per-run table in
   the BrandAgent object, never carried in intercept props (P0: concurrent runs overwrote each other's). Each session
   runs as its own OS user with its own folder, spawned from a root runner, so one person's session
   can't read another's; Bash sandboxed with no unsandboxed retry; `.claude/` not writable; WebFetch limited to a
   fixed domain list. The Worker side is the log of record; the hooks add detail but aren't the boundary.
   Proven in P0 ([S2](../decisions/p0-s2-container-guards.md)), with these requirements:
   - **The SDK sandbox is mandatory** (`enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`). Without it
     `.claude/` isn't protected: Bash could move or write it.
   - The work root is 0755 so bwrap can traverse it; each session folder uses the `stubs` layout (`root:<group> 1770`,
     a root-owned `.claude/` with the protected names pre-created).
   - The audit hook runs with `onFailure: 'block'`: with `continue`, a failed audit let a write through.
   - Built-in tools are locked with `tools: [the decided 20]`. Four of the 20 didn't register headless
     (AskUserQuestion, ListMcpResourcesTool, ReadMcpResourceTool, WaitForMcpServers); P3 re-checks them with the real
     `inhouse` MCP server and a `canUseTool` callback.
   - Skills and plugins are locked with `skills: ["dataviz", <ours>]`, `settings.skillOverrides` off for the other 15
     bundled skills and `settings.enabledPlugins` false for the three built-in plugins. The `skills` list alone hides
     skills from the model but doesn't block a typed `/command`. `dataviz` stays bundled: its licence forbids copying.
   - System files such as `/etc/passwd` stay readable from scripts (denying them breaks python); nothing of ours lives
     there.
5. **Our `inhouse` MCP server.** The 20 approved tools in 7 categories, served by the Worker over D1. `notification_send`
   posts to Slack only in channels the admin listed and reaches a member through the in-app bell, nothing else (P5). `question_ask` is written so
   that running it unanswered is safe.
6. **Connector hub.** Holds each tool's sign-in, refreshes it and adds it to calls. Open test 6 decided it: our own
   gateway Worker, confirmed by P0 ([S4](../decisions/p0-s4-connector-hub.md)). Self-hosted Executor doesn't fit
   Cloudflare as it ships. A `SignIn` Durable Object per connector account holds the token in its storage, never in
   isolate memory. Shopify uses Dev Dashboard apps with the client credentials grant (24 h tokens the hub refreshes);
   each brand's app declares level 1 protected customer data (level 2 only if a feature needs names or addresses) and
   includes `read_returns` in its read scopes. Code mode runs at the hub in a Dynamic Worker with no network, reaching
   the tool only through a read-only binding: over the full order list of a seeded dev store (about 88K characters
   raw), 199 to 1,131 characters reached the model, and Haiku 5.5 picked the code-mode tool every time.
   Slack (P0 S4): Slack's own hosted MCP server sits behind the hub. Slack has no dynamic client registration, so the
   hub runs the OAuth itself with a one-time `state` check, and the MCP TypeScript SDK's client is used only to proxy
   calls. The token is encrypted in a Durable Object. The proxy is read-only by default: of Slack's 27 tools (14 read,
   13 write), write tools appear only with a per-run grant the server sets and the model can't, and under the Agent
   writes decision that grant goes to the server's outbox and `notification_send` path, never to the runner
   (confirmed, Wasim 2026-11-19). Each
   brand's Slack app gets least scopes, 5 for Watch plus notifications (`search:read.public`, `channels:read`,
   `channels:history`, `users:read`, `chat:write`). The hub lists only the tools the brand allows, since Slack's full
   list adds 13K to 99K input tokens per question. Private-channel search is a hub policy per brand, not the model's
   choice. Slack search ANDs keywords, so wording mismatches miss: P5 adds a better tool description or a hub fallback.
   With token rotation off a user token doesn't expire; with it on, tokens last 12 h with single-use refresh tokens, so
   the refresh path saves the new pair atomically. One internal Slack app per brand at first, a Marketplace app later
   (Wasim, 2026-11-19). Tokens are encrypted with AES-GCM under a versioned key held as a Worker
   secret. **The runner's scope is read only, code mode included.** Tool writes exist only on the outbox path.
7. **Approvals and the outbox.** `approval_request` stores a typed action: operation, connector account, arguments,
   recipient, money and a revision. A server table per operation says whether it moves money, reaches a customer, is
   reversible, and whether the tool honours an idempotency key; an operation not in the table always waits. The card a
   person approves is rendered by the server from those typed fields, and `approve(id, ifRev)` binds the approval to
   that exact revision. Approving writes the dispatch intent in the same D1 transaction and sets `sendAt` (the
   server's clock plus 10 seconds). At `sendAt` the alarm claims the row with one conditional update (approved, not
   undone, not paused, now past `sendAt`), marks it `sending`, and calls the tool. Undo is the opposite conditional
   update and wins only before the claim. A tool with idempotency gets a retry with the same key; without it, an
   unclear result becomes `needs_check` for a person, never an automatic resend. A sweep finds approved rows whose
   alarm was lost. Guarantee: **at most once**, with every uncertain send shown to a person. Undo after a send is a new
   compensating action through the same approval path, where the tool allows one.
8. **Routines and waits.** Routine schedules live in D1; the BrandAgent alarm wakes for the next due slot and starts
   one run per slot, keyed by the slot so a repeat alarm can't run it twice; each routine has a missed-run rule.
   Routine runs are single-shot `query()` calls. `question_ask` in a routine defers the tool call, so the run ends with
   `tool_deferred` ([hooks](https://code.claude.com/docs/en/hooks)); the answer resumes the session. The docs say
   deferral only works with one tool call in the turn. P0 saw the SDK honour it beside a parallel call, unlike its
   docs, so the runner keeps its own one-call check (treat `question_ask` beside other calls as not deferrable, or
   reject the turn). The wait is capped (7 days, then the routine run is closed and the person told). Proven across a
   container restart in P0 ([S1](../decisions/p0-s1-runner.md)).
9. **Run stage.** The same outbox with a policy check before the claim: the job is on the brand's list, the action
   reserves its share of the daily action limit and the largest-restock limit atomically in D1, and money and customer
   actions always wait. Every handled job is logged with Undo where the tool allows. Pause stops new runs, interrupts
   live ones and stops the outbox at the claim.
10. **Usage and the spending cap.** Before each run the Worker reserves budget in D1 with one conditional update and
    passes the reservation as `maxBudgetUsd`. Results settle as idempotent deltas, because a resumed session's totals
    can include earlier spend and a crash can leave none
    ([cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)); a run with no result is settled from
    the egress entrypoint's own tally of model responses (P3). The SDK's limit is an estimate and the response that crosses it completes, so the
    cap is stated as "hard at the start of a run, may overshoot by one response per live run". The gateway
    [spend limit](https://developers.cloudflare.com/ai-gateway/features/spend-limits/) is a backstop, not the cap.
11. **Audit log.** Append-only D1 table written by the Worker for every tool call, outbox step and person's action,
    with arguments redacted by field. No code path updates or deletes it and SQL triggers reject both. A daily copy
    goes to R2, so a D1 restore can't rewind it.
12. **Files.** R2. Library rows in D1. Downloads go through the Worker with a permission check.
13. **Memory.** D1 with FTS5 for `memory_search` and `history_search`. A brand fact waits for an admin's OK, a person
    fact counts at once. `memory_save` refuses customer personal data.
14. **Models.** The brand's AI Gateway with the brand's Anthropic key stored there
    ([Anthropic provider](https://developers.cloudflare.com/ai-gateway/usage/providers/anthropic/)) and payload
    logging off ([logging](https://developers.cloudflare.com/ai-gateway/observability/logging/)). Bedrock by switch
    (BD9; WebSearch isn't available there, [Bedrock](https://code.claude.com/docs/en/amazon-bedrock)).

**Auth.** Access in the brand's account, with the brand's identity provider (Google Workspace or Microsoft Entra, MFA
from there); one-time PIN only where a brand has neither. Every signed-in person takes an Access seat
([FAQ](https://developers.cloudflare.com/cloudflare-one/faq/getting-started-faq/)), Inhouse team members included. The
Inhouse team comes in through a separate Access application pinned to our identity provider, which is what gives the
role; an email row alone never does. Monitoring and the QA gate use service tokens, each mapped to a named principal
with its own routes. Locally and in tests the Worker verifies against a test issuer; a deploy check fails if a brand
deployment would accept any issuer but its Access team. The brand deployment has no workers.dev or preview hostname.

Behind this UI contract sits the Worker-runner protocol, which P0 made mandatory from P3, not optional: a deploy
restarts live containers, and the new image reaches containers about 6 minutes after the Worker goes live
([S1](../decisions/p0-s1-runner.md)). So the runner reports its protocol version, the Worker accepts the current and
previous version, and C5's events carry a protocol version for the browser.

## Tests that keep the two in sync

1. **One schema.** Requests, responses and events are defined once (zod) in a shared folder that the app and the Worker
   import, and parsed at the API boundary in both directions.
2. **Contract suite.** One Vitest suite run against `MockAgent` and the real client, and it parses every value and
   event both return through the shared schema, so the mock can't drift either. The real client runs against the
   Worker under `wrangler dev`, with a seeded D1, the test issuer and the scripted model. It covers stable snapshots,
   notices and optimistic rollback; fast-check covers revisions and reattach ordering.
3. **Scripted model.** A fake Anthropic endpoint, test and preview only and checked out of the product bundle, keyed by
   scenario and turn; a miss fails the test. The real runner, tools, hooks and alarms run; only the model is fixed.
4. **API specs.** Playwright `request` specs: a missing or bad JWT gets 401 on every route and on the socket; every
   route and object against every role, including two people with the same role (one can't open the other's chat);
   revocation closes sockets; revisions and conflicts; hold timing, Undo against the claim, `needs_check`; `cap_reached`.
5. **E2E on per-PR previews.** In the sandbox account. Previews give each PR its own Durable Objects and container
   ([Previews](https://developers.cloudflare.com/workers/previews/resources/), container support listed as partial);
   `preview.yml` creates a D1 database per PR, migrates and seeds the invented brand, binds it and deletes it with the
   preview; R2 uses one sandbox bucket with a per-PR prefix (fine there, since the account holds only invented data).
   Hardening's `preview.yml` deploys only a generated wrangler config equal to `main`'s (no bindings, routes or build
   steps; `previews: {}` required), a security gate (decision 0011), so a per-PR D1 binding would have to change that
   workflow on purpose through a bootstrap PR. Decision Q1 later dropped the per-PR product preview, so the demo
   preview's gate stays as it is.
   Previews sit behind Access; the QA gate uses its service token. The existing UI specs run as a `real` Playwright
   project wherever a screen is real. If containers in previews fail P0, P3 onward are proven under `wrangler dev` and
   on the house deployment instead; never by pointing a preview at the house runner.
   **P0 result ([S3](../decisions/p0-s3-previews.md)):** Durable Object alarms and a per-PR D1 work in Previews. The D1
   binding is static config, so CI generates a per-PR config (the `previews: {}`-only gate changes), and cleanup also
   deletes leftover container apps. Containers in Previews didn't start: a container must be declared from a Preview's
   first deploy (else `DURABLE_OBJECT_NOT_CONTAINER_ENABLED`), and even then it wasn't running after 20 minutes. So the
   fallback applies: container E2E runs under `wrangler dev` and on the house deployment, with a retest at P2. Access
   with a service token is unverified (dashboard only) and is checked at P2.
   Previews keep the scripted model. Any E2E that calls a real model (under `wrangler dev` or on the house deployment)
   runs on Sonnet 5.5 at medium (Wasim, 2026-11-19).
6. **Nightly on the house deployment.** The container guard tests (acceptance 8), connector tests against the Shopify
   development store and official MCP test modes (these join in P4 and P5), and the agent evals. S2's probe set is
   the start of the guard tests; the "no token reachable" check allows the sandbox's own proxy credential, which opens
   only the allowlist proxy. Connector tests use a seeded dev store as a fixed fixture and never reseed per run: dev
   stores take 5 orders a minute (measured in P0), and Shopify won't backdate refunds, so dated refunds in test data
   are made on their day. Tests and evals that call a real model run on Sonnet 5.5 at medium, not Haiku (Wasim, 2026-11-19).
7. **Agent evals.** A graded set run before a model, prompt or SDK change and nightly: tool choice with our names,
   memory recall, routine creation, cost per conversation, an injection set (tool data that tells the agent to send,
   refund or widen recipients) and an exfiltration set (tool data that tells it to fetch a URL or message someone
   outside the team). Any bypass fails. Results are kept. Evals run on Sonnet 5.5 at medium unless the run compares
   models (Wasim, 2026-11-19); Haiku results from P0 are rechecked on Sonnet before they shape the engineering.
   **Seed from P0 ([S5](../decisions/p0-s5-memory-tool-choice.md)):** S5's 43 cases (recall, recall across chats, tool
   choice against look-alikes, connector choice, negatives) and its code-only grader are the start of this suite, after
   three grader fixes. Sonnet 5.5 at medium scored 94% (recall 91%, tool choice 92%, negatives 100%), about $1.6 a
   full run. That is a baseline, not the model choice. Our tool names hold and tool search found every deferred tool.
   S4's Slack supplier-delay case (a wording mismatch that keyword search misses) joins the set in P5.
   The "search memory first" prompt rule is softened (decided, Wasim 2026-11-19): the agent searches memory when the
   question could depend on saved context, not on every chat. The old rule added about one turn to chats that weren't
   about recall. P3's eval checks that recall doesn't drop.

## Releases across accounts

Version URLs aren't generated for Workers with Durable Objects
([previews](https://developers.cloudflare.com/workers/configuration/previews/)), container images roll out with
`wrangler deploy` after the Worker ([rollouts](https://developers.cloudflare.com/containers/platform-details/rollouts/)),
and rollback is blocked across Durable Object class changes
([rollbacks](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/rollbacks/)). So:
- The house deployment is the gate: a release deploys there first and runs the ship specs and a smoke before any brand.
- The Worker and the runner speak a versioned protocol and the Worker accepts the current and previous version, so a
  Worker that activates before its image still works. P0 confirmed the gap: the image reached containers about 6
  minutes after the Worker, and the rollout restarted a live container. So each deploy pauses new runs and drains live
  ones, deploys with `--containers-rollout=immediate`, then sends a warm-up run to each runner.
- Stored run events carry a version; an old tab reattaching gets events it can read or a reload prompt.
- Rollback is a redeploy of the previous release tag. D1 migrations are forward only (add, backfill, remove later),
  and Durable Object classes are only ever added within a release (no rename or delete), so the previous tag can
  always be redeployed.
- One workflow in the private ops repo deploys a release to each account in turn, Wrangler only.
- The hardening plan's Version URL smoke stays for the demo; the product's smoke runs on the house deployment.

## Production readiness (before any real brand data)

- **Privacy.** A data map and a data-flow document per brand (what each store holds, where it's processed, for how
  long, who sees it); payload logging off; no customer personal data in memory; the brand's sub-processors listed for
  its records; Shopify's protected customer data rules and mandatory privacy webhooks met (each brand's app declares
  level 1, with no names, emails, phones or addresses; level 2 only if a feature needs them; `read_returns` in its
  read scopes).
- **Retention.** Per-brand settings with defaults for chats and transcripts, run events, files and the audit log. The
  BrandAgent alarm deletes what's past retention daily; R2
  [lifecycle rules](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) back it up.
- **Export and deletion.** A brand export and a person's export or deletion are tested runbook scripts. A member's
  removal ends their access at once. Brand offboarding and any teardown delete container applications explicitly:
  deleting a Worker doesn't delete them, and they stay with their pre-placed instances until deleted on their own
  (`DELETE /accounts/<id>/containers/applications/<app id>`). The same holds for a deleted Preview's container app.
  The teardown script lists container apps before and after, and fails if any remain.
- **Backups.** D1 Time Travel (30 days, [docs](https://developers.cloudflare.com/d1/reference/time-travel/)); D1
  export doesn't support databases with virtual tables such as FTS5
  ([limits](https://developers.cloudflare.com/d1/best-practices/import-export-data/)), so the nightly backup writes
  the canonical tables to R2 and a restore rebuilds the search index. Durable Object point-in-time recovery
  ([docs](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)). After any restore the outbox
  stays paused until restored actions are checked against the tools' records and later deletions are applied again.
  A restore drill across D1, R2 and Durable Objects on the house deployment before the first brand.
- **Limits.** Strict limits (runs at once, actions per day, spend) in the BrandAgent object and D1. No per-member rate
  limit for now: every caller is a signed-in team member. Runs at once follow the runner pool: 25 per standard-4
  container, at least 2 containers per brand, `max_instances` at least 3 times the need (P0 S1). Custom instance types
  need at least 3 GiB per vCPU.
- **Incident runbook.** Pause a brand's agent, rotate the model key and tool tokens, remove a member, redeploy the
  previous release, restore. Each step rehearsed once on the house deployment.
- **Cost controls.** The cap with reservations, `maxTurns` and `maxBudgetUsd` per run, the container's inactivity
  timeout (set again on every run), fill-first routing so extra containers sleep off-peak, the gateway spend limit as
  backstop, the alert at the Settings threshold.
- **Monitoring.** A health route per deployment behind a service token, read by a scheduled monitor in the private ops
  repo; it reports run failures, stuck runs, `mirror_error`, container restarts, `needs_check` rows and a brand running
  below its target container count (placement refusals are expected; a lasting shortfall is an alert). Errors stay in
  Workers Logs in the brand's account (kept 7 days, and its pricing changes on 2026-12-01:
  [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)). No chat or customer content leaves the account for monitoring.

## Risks

- The Agent SDK is 0.x and runs a CLI; hangs and breaking changes are possible. Pin it; run the evals on every bump.
  P0 already found its behaviour ahead of its docs (deferral beside a parallel call), so the runner keeps its own
  checks.
- The new container scheduling policy and snapshots are beta; we use neither until GA. Containers in previews didn't
  start in P0 (fallback in Tests, 5).
- Container placement is the main capacity risk: refusals are normal, a new container app's capacity grew over its
  first 30 minutes, and how `max_instances` relates to placement is undocumented. Route around refusals, alert on a
  shortfall, size `max_instances` at 3 times the need, and ask Cloudflare before P3.
- Session mirroring is best effort; the checkpoint with repair and the `mirror_error` alert cover it. A hard
  container kill loses the live turn's transcript until a mid-turn flush is proven in P3.
- Each brand sets up its own Cloudflare and Anthropic accounts; the onboarding checklist covers it.
- The SDK runs under Anthropic's commercial terms, on each brand's own API key.
