# P7: Run (`fleet/run`)

Status: draft, 2026-11-19. Phase plan under the backend plan (`docs/plans/2026-11-19-backend.md`, Architecture 9).
Common rules are in its "Phase schedule (waves)" section.

## Goal

At the Run stage the agent handles the brand's agreed jobs by itself, inside its limits, with every step logged and
undoable where the tool allows, and Pause stops everything.

**Success measure (the real slice):** an allowed restock runs by itself and shows in Activity; a refund still waits.

## Scope

In:
- **The policy check** before the outbox claim: the job is on the brand's list; the action reserves its share of the
  daily action limit and the largest-restock limit atomically in D1; money and customer actions always wait.
- **Handled jobs:** each logged in Activity with Undo where the tool allows (a compensating action through the outbox).
- **Pause:** stops new runs, interrupts live ones and stops the outbox at the claim; resuming restarts nothing on its
  own.
- **Run settings:** the job list and limits on the Inhouse team pages, read-only for admins.
- A Run-stage eval set: tool data that pushes the agent past its limits or off its job list.

Out: new connectors or operations (each joins the operation table when a brand needs it).

## Browser scenarios (`e2e/ship/run.spec.ts`, desktop and phone, fixture store, scripted model)

- S1: An allowed restock runs by itself and shows in Activity with Undo.
- S2: A refund drafted at Run still waits for approval.
- S3: The next restock past the daily limit waits instead of running.
- S4: Pause stops a live run and a pending send; Resume starts nothing by itself.
- S5: Undo on a handled restock creates its compensating action and Activity shows both.
- S6: As an admin, the Run settings are read-only.

## Acceptance

1. A job inside its limits runs by itself; one outside the list or past a limit waits; money and customer actions
   always wait.
2. Limit reservations are atomic: concurrent actions never exceed the daily or largest-restock limit (a concurrency
   test with parallel claims).
3. Pause stops new runs, live runs and the outbox at the claim; nothing sends while paused.
4. Every handled job is in Activity and the audit log; Undo works where the tool allows and is absent where it doesn't.
5. The Run-stage eval set has zero limit or list bypasses.
6. API specs and the contract suite pass for P7 methods; the demo is unchanged.
7. QA PASS and the ship recording on S1 to S6.

## Must not

No action outside the job list or limits; no money or customer action without a person; no send while paused; no
limit enforced only in the UI.

## Risks

- Limits under concurrency: one conditional update per reservation, and a property test over interleavings.
- Undo semantics differ per tool; the operation table states it, and the UI shows Undo only where it's real.
